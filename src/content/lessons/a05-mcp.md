T01 讲的工具调用有个隐含前提：工具就在你的应用进程里。现实是工具长在别人家——数据库在 DBA 的域里、文件在用户机器上、GitHub 在微软的云上。每接一个新工具就写一份胶水代码：鉴权、参数映射、错误处理各写一遍，M 个应用 × N 个工具就是 M×N 份胶水，而且每一份都要随任意一端升级而维护——集成爆炸。MCP（Model Context Protocol）的答案是把 M×N 压成 M+N：工具方实现一次 server，应用方实现一次 client，两端只对协议负责。上方的泳道时间轴走完一次 MCP 工具调用的完整往返。

## 三角色：host、client、server

MCP 的角色表有三个名字。host 是用户面对的应用——桌面助手、IDE、你写的 Agent 服务；client 是 host 内嵌的协议连接器，每个 server 对应一条 client 连接；server 是能力的提供方——文件系统、数据库、GitHub、Slack，各自把能力封装成一个独立进程，可以由任何人用任何语言实现。演示里 host 启动时装配两条 client 连接，分别握手文件系统 server 与数据库 server。理解三角色的关键是「协议在 client 与 server 之间」：host 与模型不感知协议细节——对模型来说，MCP 工具与 T01 进程内工具没有任何区别，都是工具清单上的一行，这正是 MCP 能平滑接入既有 Agent 架构的原因。这就是「通用插座」的含义：插头形状标准化，电器（工具）与电源（应用）互不迁就。

## 能力协商与三类能力

握手（initialize）是 MCP 的第一幕：client 与 server 交换协议版本与能力清单——server 报出自己支持什么（tools / resources / prompts 三类能力），client 确认自己懂哪些协议版本。这一步是一次性的：连接建立时发现能力，之后调用按需发生——发现的成本付一次，调用的路径走千遍。三类能力各管一摊：tools 是可执行的动作（查询订单、写文件），由模型决定何时调用；resources 是可读取的数据（文档、记录），由应用决定何时取用；prompts 是预制的提示模板，由用户主动选用。演示里两个 server 各自报出清单，host 把它们合并进发给模型的工具列表——工具发现对模型透明。这层协商还有工程含义：能力清单是动态的，server 可以在运行中增减工具，host 侧的工具列表随之刷新，不需要重新发布应用。

## 一次协议化调用的往返

演示的主线是一次跨两个 server 的任务：「查订单总额并把明细存成文件」。流程前半段与 T01 完全同构：合并工具清单发给模型 → 模型回 tool_use 申请——模型侧的一切照旧。后半段出现差异：host 不再自己执行，而是把申请经 client 转发到归属的 server——数据库 server 执行查询、文件系统 server 落盘明细，结果原路经 client 回填 host，再按 tool_use id 配对回灌模型。注意有两层「配对」：模型侧的 tool_use/tool_result 配对（T01 的规则）与协议侧的请求/响应配对——两层各自独立，互不干扰。协议换来的能力是执行位置的自由：工具可以跑在本地进程、另一台机器、另一个组织的云里，调用方的代码一行不改。

## 与普通 tool call 的异同

把异同列清楚。相同的是模型侧的一切：工具清单、tool_use 申请、tool_result 回填、id 配对——MCP 对模型完全透明，这也是协议设计的克制之处：不动模型交互，只动集成层。不同的是集成侧的一切：工具从「进程内函数」变成「跨协议的服务」，多了能力发现、版本协商、生命周期管理（连接的建立与断开、中途掉线的重连）；错误处理也多了一层——server 返回的协议级错误（工具不存在、参数非法、权限拒绝）要被 client 翻译回模型能理解的 tool_result 错误文本，翻译时别丢可操作线索（T03 的教训跨层适用）。延迟特性也随之改变：进程内调用是纳秒级，协议调用有网络往返，工具的时延预算（T01）在 MCP 场景要重新标定。安全边界也随之移动——server 是独立的第三方代码，跑在 host 之外。判断是否需要 MCP 的标准因此清晰：工具只在自己应用里用，进程内函数更简单；工具要开放给多个应用、或由第三方维护，MCP 的标准化才开始挣钱。

## 安全面：最小授权

MCP 的开放性自带安全命题：server 是第三方代码，且能力常常直通敏感资源——文件系统、数据库、企业消息。三条底线：其一，能力授予最小化——按需逐项开放工具，演示的 host 只授了 query_orders 与写文件的权限，而不是「整个数据库」；其二，人工闸门前置——高危工具（写、删、发送）在 MCP 之上仍要套 A06 的审批闸门，协议不替你做治理；其三，供应链审视——安装第三方 server 等于引入第三方依赖，来源与更新渠道要审计，server 拿到的凭据也要按最小权限发放（给文件系统 server 一个专用目录，而不是整个家目录）。MCP 解决的是「怎么连」，不解决「该不该连」——后者永远是应用方的治理问题。
