上一课把一次工具调用拆成了完整往返：申请、校验、执行、回填。这一课回答一个自然的追问：模型一次给出两个、三个申请怎么办？上方的泳道时间轴演示了一个「对比两地天气」的任务——模型在同一条回复里产出两个 tool_use，客户端并发执行、按 id 逐一回填，最后汇总作答。全程只花了一轮串行查询的时延，而不是两轮相加。这是压总时延最直接的一招，但它的使用条件比看上去苛刻：用对了省一半时间，用错了直接制造错误。

## 一次输出多张申请

模型完全可以在一条回复里放多块 tool_use：任务天然可拆时它就会这么做——对比两地天气、同时查三个字段、给两份文档各做一次检索。每块申请各有自己的 id 与 input，互不引用；这意味着从模型视角看，它们谁也不等谁。任务描述会影响它的选择：问句里出现「对比」「分别」「都查一下」这类词，拆成并行申请的概率明显升高；反过来，把任务写成带先后顺序的步骤，模型多半会串行申请。要注意的是「要不要并行」的决定权不在模型：它只负责把申请一次性摆出来，怎么执行是客户端的调度问题。有些 API 允许用参数关掉并行输出，强制模型一次只申请一个——适合工具之间会互相干扰、或下游并发容量有限的场景。

## 独立才可并发

并发的判据只有一条：后一个申请的参数是否需要前一个的结果。两个城市的名字都是模型直接给出的常量——相互独立，可以同时发出。反过来，「先查城市代码，再用代码查天气」里第二个申请的参数在第一个结果回来之前根本写不出来，只能串行。判断错了的代价是真实的：把有依赖的申请并发出去，客户端要么拿不到必要参数直接失败，要么用自己的猜测填补参数——后者更糟，错误会在下游静默传播。所以并发前的那一步「依赖检查」不是仪式，是正确性关口；这一步的判断逻辑写在代码里，逐块对照 input 里的字段来源，几十行就能覆盖绝大多数场景。

## 按 id 配对回填

并发世界里完成顺序不可控：发出去的是 #1、#2，回来的可能是 #2 先到。客户端按 tool_use_id 暂存每个结果，等全部到齐后再一并回填——部分到齐就急着回填，模型会带着不完整的观察作答。id 配对是乱序世界里保持正确性的锚，这也是上一课说 id 看似琐碎、实为命门的原因。实现上通常是一个以 id 为键的暂存表加一个「全部到齐」的计数器，十几行代码的事，但缺了它，并发就成了事故来源。每个并发任务还要带自己的超时：整个批次超时了，把到齐的部分按原样回填、没到齐的按超时错误回填，让模型在残局上做决定——比整批悬挂强得多。

## 有依赖时必须等

任务真正有依赖时，正确姿势是拆成多轮：第一轮发出申请、等结果回填，模型再基于结果发起第二轮申请。串行多花的时间是买正确性的钱，省不掉。工程上值得做的是把「等待」压缩：依赖链上只有第一环必须串行，链条走完后新长出来的独立分支又可以在下一轮并发。另外要为「部分失败」做设计——两个并发查询一个成功一个超时，回填时用 is_error 标记失败的那个（这正是 T03 的主题），让模型基于一半事实和一条错误信息决定下一步，而不是让整批作废。

## 并发是客户端的自由

把视角拔高：模型只管申请，怎么执行——并发、串行、排队、限流——全是客户端的自由与责任。同一个「两份申请」，测试环境可以串行跑，生产环境可以带并发上限的线程池跑，模型对此一无所知也不需要知道。并发之外还要补一笔成本的账：并发不改变 token 总量，却改变了时延结构——把一批任务从串行改成并发，省的是墙钟时间，多占的是下游瞬时容量。下游有并发上限时，客户端要做的是带闸门的并发：线程池限到 N 个在途请求，多余的排队，避免一波并发把对方打挂——那是把时延优化变成故障制造。这层自由度是函数调用架构真正的杠杆：不改一行 prompt，只改客户端调度，就能把一组任务的耗时从串行相加压成取最慢一个。下一课看这条链路出故障时怎么办——失败是常态，护栏是必修课。
