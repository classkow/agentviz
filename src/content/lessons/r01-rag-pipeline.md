## 为什么需要开卷：闭卷模型的两个缺陷

把 LLM 想成一位只读过训练截止日前所有书的闭卷考生：此后发生的事、没进过语料的私有资料，它一概不知道——这是知识冻结。更麻烦的是第二点：闭卷答题时它不会交白卷，缺什么就按语言惯性补什么，答得流畅却毫无依据，这就是幻觉。问「我们公司第三季度的回款政策」，模型没见过这份文件，得到的只会是像模像样的泛泛而谈。RAG（检索增强生成）的思路不是去改造模型，而是换一种考试形式：先从资料库里把相关段落查出来，连同问题一起交给模型，让它开卷作答。也要划清反例：通用闲聊、纯推理题这类不依赖私有或时新资料的任务，挂上检索反而引入噪声——召回的段落和问题不沾边，模型还得费劲忽略它们。另外，幻觉与知识冻结要分开归因：前者是生成时的编造倾向，后者是语料的时间与覆盖边界；RAG 补的主要是后者，对前者只起约束作用。

## 索引期：把文档压进几何空间

索引期是离线的准备工作，相当于编译期：离线预处理跑一次，产物是可复用的索引文件，查询期（运行期）直接加载使用。流程四步：先清洗文档，去页眉页脚、表格转文本；再切块，常见配置是每块约 512 token、相邻块重叠 64 token——重叠保证恰好跨界的句子在相邻两块里各留一份，不会被拦腰切断；然后调用嵌入模型，把每块文本编码成一个高维浮点向量，语义越接近、向量之间夹角越小，文字从此变成可计算的几何坐标；最后把向量、原文、元数据三件套写入向量库。这里有一条铁律：嵌入模型一旦选定即冻结，建库与查询必须用同一个，不同模型的向量空间互不兼容。索引期是一次性成本，只在知识库更新时重跑。块大小本身就是一组取舍：块切得太小，一句话的语义被拆散，检索回来的片段缺上下文；块切得太大，相关段落被淹没在无关文字里，既稀释检索精度又浪费窗口。冻结嵌入模型的另一面是升级成本：想换更强的嵌入模型，等于整套索引推倒重建——旧向量在新模型的向量空间里没有任何意义。

## 查询期：一次开卷请求的四步

查询期是运行期，每次提问都完整走一遍，共四步。第一步把用户问题用同一个嵌入模型编成向量，只处理一句话，毫秒级完成；第二步拿它去向量库做余弦相似度检索，取最相近的 top-k 段落，连同原文与元数据一起返回；第三步拼增强 prompt：system 写明「仅依据以下资料回答，标不出来源就明说」，后面接上检索到的资料原文与用户问题；第四步按 E01 讲过的老协议 POST /chat/completions 发出，流式收回结果。RAG 的关键认知在这里：它不发明新的调用协议，改写的只是请求体内容——messages 里多了几段检索资料，temperature 通常调低（如 0.2）以减少无据发挥。四步各有失败模式：问题表述太口语，嵌入向量可能偏离库内文档的语义区；检索落空，只返回一堆低分块；资料拼得太多，撑爆窗口被截断；模型无视资料自由发挥。前三步靠检索侧的工程手段防，最后一步只能靠 prompt 约束与后验校验。[→ 回看演示第 11 步](#demo-step-11)

把这三段写成一份可照抄的序列（数字全部取自上方演示）：

```json
{
  "1_retrieve": {
    "embed_query": {
      "model": "<与建库时冻结的同一个嵌入模型>",
      "input": "第三季度的回款政策是什么？"
    },
    "vector_dims": 1536,
    "top_k": 5,
    "similarity_scores": [0.91, 0.88, 0.85, 0.71, 0.42]
  },
  "2_rerank_optional": {
    "input": "<上一步召回的 5 段候选>",
    "note": "本课演示不含这一步：这里只按嵌入相似度排序。重排序模型会带着 query 与候选文本再打一遍分，见 R04。"
  },
  "3_assemble": {
    "messages": [
      {
        "role": "system",
        "content": "仅依据以下资料回答，标不出来源就明说\n<docs>…5 段检索原文 + 元数据（文档名/章节/日期）…</docs>"
      },
      { "role": "user", "content": "第三季度的回款政策是什么？" }
    ],
    "temperature": 0.2
  }
}
```

## 相似度与 top-k：检索质量的两个旋钮

余弦相似度衡量两根向量夹角：接近 1 表示方向几乎一致、语义高度重合，接近 0 表示基本无关；检索就是用 query 向量在库里找得分最高的几条。top-k 是第一个旋钮：k 太小会漏掉关键资料，答案残缺；k 太大则稀释上下文——演示数据里第 5 条得分已跌到 0.42，属于弱相关，把它拼进 prompt 不但帮不上忙，还挤占上下文窗口、诱导模型牵强附会。实际工程会给相似度设阈值，低分块宁可丢弃，不做凑数的人情。这不是 RAG 独有的取舍：上下文是稀缺资源，往里放的每一块都要值回它的 token。阈值与 top-k 通常联用：先按分数阈值滤掉弱相关，再在幸存者里取前 k 条——一道闸管质量下限，一道闸管数量上限。这笔账和 E02 是同一本：每一块拼进 prompt 的资料都要占窗口、付输入费，检索精度直接决定这笔钱花得值不值。

## 可溯源，以及开卷救不了的事

开卷考试最大的红利是可溯源：答案能带上「【来源：《回款管理办法》§3.2】」这样的标注，用户可点开原文核对，这在制度问答、客服与合规场景里是闭卷模型给不了的东西。但开卷救不了检索落空：如果 query 与库内内容在语义上不沾边，检索环节取不回有用资料，模型仍可能借着零星弱相关碎片硬答一段，幻觉并未根除。防线只有一道：把「资料不足就明说找不到」写进 system prompt，并把「未找到」视为合格回答而不是失败。在合规场景里，溯源链要闭环才算数：答案标注来源、来源可点开原文、原文版本与检索时间留档，审计时才能逐条复核。「未找到」也因此有了正当性——宁可交回一个明说缺资料的答案，也不交一个编出来的完整答案。本课是模块 R 的总览，后续两课将深入：R02 讲语义空间与嵌入选型，R03 掰开切块与检索策略。

> **带走三句话**
>
> RAG 不改造模型，只换考试形式：先把相关段落查出来，连同问题一起交给模型，让它开卷作答。
>
> 建库是编译期、查询是运行期：索引离线跑一次就能反复复用，查询这条链路每次提问都要完整走一遍。
>
> 开卷的红利是可溯源，天花板是检索质量：检索落空时模型照样能编出一段，所以「资料不足就明说找不到」必须写进 system prompt，并把「未找到」当成合格答案而不是失败。
