A01 把 Agent 还原成「LLM + 循环 + 工具」，A02 回放了一整集任务；这一课把其中最小的零件拆开看：一次工具调用（tool call）的完整往返。它小到只有一个来回，却承担了 Agent 与真实世界之间全部的信息交换——模型的所有「行动」都从这里出、所有「观察」都从这里回。上方的泳道时间轴把这次往返摊开在五条泳道上——用户、应用、LLM、工具集与数据库——从声明工具清单到回填结果，一共十一个动作，每一步的职责归属都值得看清。

## 工具是请求里声明的函数清单

工具不是装进模型里的插件，而是随每次请求发送的声明：一个 tools 数组，每一项带三样东西——name（函数名）、description（写给模型看的用途说明）、input_schema（用 JSON Schema 写的参数约束）。这三样全是「文档」：description 决定模型何时想起这个工具，input_schema 决定模型怎么填参数，写得含糊模型就用错。举例说，「查询订单」就是个坏 description——模型不知道它能不能查退款、能不能跨季度；而「按区域与季度查询已支付订单的聚合金额，不支持退款单与单笔明细」就是好 description——边界写清楚，模型在边界外自然去想别的路。input_schema 同理：枚举值列出来、字段写上说明，参数错误率立刻降一个台阶。声明与请求同进同出，意味着模型从头到尾接触不到任何真实代码——它看到的只是清单和说明，函数体永远留在你的应用里。

上面演示第 2 步发出去的就是这一段（字段名对齐 Anthropic 的工具声明格式）：

```json
{
  "tools": [
    {
      "name": "get_order_total",
      "description": "按区域与季度查询已支付订单的聚合金额，不支持退款单与单笔明细",
      "input_schema": {
        "type": "object",
        "properties": {
          "region": { "type": "string", "description": "销售区域，例如「华东」" },
          "quarter": {
            "type": "string",
            "enum": ["Q1", "Q2", "Q3", "Q4"],
            "description": "财年季度"
          }
        },
        "required": ["region", "quarter"]
      }
    }
  ]
}
```

## 模型输出的是申请，不是执行

模型「调用工具」这句话容易误导：它输出的不是执行结果，而是一块结构化的 tool_use 申请——type 标记块类型，id 是这次申请的唯一编号，name 指向清单里的某个函数，input 是它按 schema 生成的参数，同时响应里的 stop_reason 标成 tool_use，意思是「我在等执行结果」。收到申请后，真正动手的是你的代码：校验参数、执行查询、拿到结果。执行权永远在客户端，这是设计而非限制——权限、计费、审计、限流全部发生在你的地盘上，模型从不直接触网，它只会「申请」。换个角度看，这也是让模型安全接入真实世界的唯一可行架构：数据库凭据、内网地址、删除权限根本不必写进任何 prompt，模型想用也拿不到；它能做的只是填一张申请单，批不批、怎么批，全在你的代码里。[→ 回看演示第 4 步](#demo-step-4)

```json
{
  "role": "assistant",
  "stop_reason": "tool_use",
  "content": [
    {
      "type": "tool_use",
      "id": "toolu_01A",
      "name": "get_order_total",
      "input": { "region": "华东", "quarter": "Q2" }
    }
  ]
}
```

## 回填：tool_result 与 id 配对

结果拿到后，以 tool_result 块的形式追加进 messages 再发回模型：tool_use_id 必须与申请时的 id 配对，content 是结果本体——可以是纯文本，也可以是结构化内容。这一步是模型的「观察」来源——没有回填，模型就还停在「我在等结果」的状态；回填之后，它才有上下文继续推理或给出最终答案，此时 stop_reason 变成 end_turn，本轮交互收尾。还有一个容易忽略的规则：result 回填的顺序要与申请对应，一问一答之间不能再插别的角色消息，否则部分客户端会直接拒收；把回填做成固定函数而不是散落在各处的手拼消息，这类坑自然消失。id 配对看似琐碎，却是下一课并行调用的命门：几个申请同时在途时，靠 id 才能知道哪条结果对哪次申请。[→ 回看演示第 8 步](#demo-step-8)

```json
{
  "role": "user",
  "content": [
    { "type": "tool_result", "tool_use_id": "toolu_01A", "content": "¥4,182,000" }
  ]
}
```

## 校验与超时：客户端的执行纪律

模型生成的参数永远不当真：input_schema 校验在执行之前，类型不对、枚举值不存在、缺字段，都在本地拒绝。执行阶段同样有纪律——超时是必须设的（外网查询没有「等它慢慢来」的选项），重试策略属于客户端工程，结果太长要截断再回填（把一个十万字的网页塞回上下文是常见的新手事故）。写操作还要多想一层幂等性：同一笔转账申请因为超时重试被执行两次，就是事故——给写操作带上客户端生成的幂等键，重试才安全。这些纪律没有一项需要模型配合，全是应用侧的普通代码，却决定了工具调用这条链路靠不靠谱。

## 最小零件，最大杠杆

把视野收回来：这次往返就是 A01 循环里转一圈的最小零件——模型申请、客户端执行、结果回填、模型继续。字段语义对齐的是 Anthropic 的 tool_use / tool_result 与 OpenAI 的 function calling：两家在字段命名上大同小异，结构上都是「声明清单 → 结构化申请 → 客户端执行 → 按 id 回填」。掌握了这个最小零件，T02 的并行调用只是「一次申请多张、并发执行」，T03 的失败重试只是「回填的是错误而非结果」——都是在这趟往返上加一层调度。再往远看一层：R 模块的检索、A 模块的循环与 MCP，全都是这个零件的不同组装方式——工具清单可以换成检索接口，循环只是把这趟往返多跑几圈。所以这一课值得慢读：后面所有模块的地基都在这五条泳道里。
