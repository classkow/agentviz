E05 讲过账单公式与杠杆排序，缓存排在第一。这一课把缓存从「一招」讲成「一套工程」：改造前后的账单对比（上方的解剖台）、命中率的经济账、什么才配进稳定前缀，以及预算护栏与成本可观测性。目标只有一个：让账单在改版与增长面前保持可预测。

## 缓存改造前后的账单

演示的构造场景：一个客服 Agent，每次请求都带着一份 4000 token 的稳定前缀——system 提示 1200、领域术语表 300、输出格式声明 500、知识库索引 2000。改造前，这份前缀每次全价重付：按示例费率 ¥4/M，单次输入 ¥0.016，10 万次调用/天就是 ¥1,600/天、约 ¥48,000/月。改造后，前缀进缓存、命中 92%：3680 token 按十分之一价折算，320 token 未命中走全价，等效计费 368×1 + 320 = 688 token——注意等效计费不是「少发」，token 照样全部发送，只是计费打折。单次降到 ¥0.002752，一天 ¥275.20、一月约 ¥8,256。前后一比：月省 ¥39,744，约 83%。这笔钱没有动一行业务逻辑，只动了「什么东西放进请求的哪个位置」。

## 命中率的经济账

缓存省钱不是线性的游戏，命中率是唯一的杠杆。把算术写成通式：等效计费 token = 前缀 token ×（命中率 × 0.1 + 未命中率 × 1）。命中率 92% 时等效 17.2%（688/4000）；命中率掉到 50%，等效涨到 55%——省的钱腰斩还多。所以值得为命中率做的投入都值得：把最常变化的字段挪出前缀、把碎片化的指令合并成稳定段落、让同类请求共享同一前缀形状。流量形态也影响命中率：请求类型越同质（同一功能的批量调用），共享前缀越稳定；一个百变入口的应用（今天写周报明天查订单），前缀天然割裂，缓存收益要先打折再评估——这类场景的正确解法是按功能拆分入口，让每条产品线有自己的稳定前缀。各家缓存还有生命周期细节要核对：缓存的存活时间（几分钟到几小时不等，超时后首个请求重新全价写入）、缓存写入本身是否加价（部分厂商对写入收 1.25 倍）、最小可缓存长度——这些参数决定「改造值不值」要按自己的流量分布精算，不能照抄别人的省百分之几。

## 逐字节一致：什么才配进前缀

缓存命中有一道铁门槛：前缀逐字节一致。一个字符之差，整段前缀全价重付。这条铁律反过来定义了「什么才配进稳定前缀」：system 块、格式声明、领域术语表、知识库索引——这些内容天生稳定，是前缀的合法居民；时间戳、用户名、会话 ID、随机数、按请求变化的检索结果——这些内容混进前缀一寸，缓存就死一寸。工程上常见的翻车是把时间戳或用户信息拼进 system——每请求前缀必变，缓存形同虚设。正确的姿势是分层：稳定内容在前、变化内容在后，把「不变的骨架」与「每请求的血肉」切开。演示第三组的 note 还列了失效场景：换模型、改 system 措辞、知识库重排，都会让缓存整段重建——改前缀是有价操作，改动前先看它值多少钱。

## 预算与限流：账单的护栏

成本工程不止省钱，还要防失控。预算护栏有三层：按请求（单次调用的成本上限——超长输入直接拒）、按用户（每用户每日配额——防单点滥用）、按全局（每日/每月总预算——接近阈值自动降级或告警）。三层的松紧要分层设定：全局预算是硬闸（触发即告警甚至停服），用户配额是软闸（超了降级不拒答），单请求上限是技术闸（max_tokens 钉死）。三层与 E05 的「输出成本不可预先精确」呼应：正因为单次成本有随机性，护栏必须是硬性的 max_tokens 与配额，而不是「尽量省」。预算的另一面是拒绝策略：超配额时是硬拒、降级（换小模型）还是排队，要按业务选——降级前先过评估集（G01），确认小模型在该任务上达标；「省钱降到不达标」的降级比超支更贵。

## 成本可观测性：先能看见，才谈优化

一切优化的前提是账单可拆解：每次调用的 usage 回执聚合出「按功能、按用户、按天」的三维账单。看板上的关键指标：单次成本分布（均值与 P95）、缓存命中率曲线（命中率突降是最有价值的多算警报——它意味着有人改了前缀）、token 用量趋势（增长要能对应到业务动作）。可观测性还负责抓住「负优化」：某次改动让输出长度悄悄翻倍，账单上会先于用户投诉现形。E05 的习惯清单到这里长成完整闭环：设计时算成本、上线后看账单、异常时查归因——成本工程不是一次性项目，是与系统共生的日常纪律。
