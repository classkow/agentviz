上一课 E03 在生成端看模型怎么从概率分布里抽签，这一课退一步看装下这一切的容器：上下文窗口。E02 说过窗口里装的是全部历史消息的 token 总和，但「总和」两个字太轻描淡写——窗口是一份有明确上限的合同，多轮对话、检索资料、模型要输出的回答，全都挤在同一份预算里。上方的窗口账本以一条客服工单对话为解剖对象，把一次 8192 预算的请求拆成五笔：system 提示、两轮历史问答、本轮新输入和输出预留。

## 一份合同，输入输出共享

窗口的准确定义是：一次 API 调用里，模型能「看到」的最大 token 数。注意「一次调用」——模型没有跨请求的记忆，所谓多轮对话，是应用把历史每一轮都重新发一遍。窗口大小是模型选型时要看的硬参数：不同模型的窗口从几千到上百万 token 不等，差出几个数量级，价格与能力也随之不同；窗口大的模型通常更贵、延迟也更高，按任务实际需要选，别无脑买最大。还要注意「输入输出共享」：窗口不是只装输入，模型要生成的回答也住在这间房子里，所以预算要分两栏记——输入侧（system + 历史 + 本轮）加上输出预留，合计不能超过上限。账本里的请求给 max_tokens 预留了 2048，输入侧就只剩 6144 可用；若不给输出留位，输出会被窗口挤掉，生成到一半戛然而止，响应里的 finish_reason 会标成 length——正是 E02 讲过的「被截断而非自然结束」。

## 塞超了的三种下场

超过窗口会发生什么？第一种是截断：输入被硬生生砍头或砍尾，模型看到的是残缺文本，答案自然驴唇不对马嘴。第二种是报错：不少 API 直接拒绝请求，返回 400 类错误，调用方拿到的不是答案而是一场空。第三种最危险——静默丢历史：为了不报错，应用层自作主张把旧历史裁掉再发，请求成功、回答流畅，但模型根本不知道自己丢过上下文，前几轮承诺过的事它一概不认。前两种至少看得见，排查信号分别是 finish_reason=length 与响应状态码，但各家的具体行为（截断还是拒收、按什么顺序裁）互不相同，接入前要查对应文档；第三种是安静的故障，日志里一切正常，只能靠评估集与上线后的用户反馈去抓。

## 历史累积：窗口消耗的主因

账本里五笔账的比例说明了一切：真正「新」的本轮输入只有 1150 token，而 system 加两轮历史占了 4050。多轮对话之所以是窗口消耗的主因，是因为历史只进不出——每转一轮，上一轮的问答就永久住进窗口，而且每发一轮新请求都要为全部历史重付一次输入费。用账本的示例费率算一笔：一份 1400 token 的 system 提示重复付费 1000 轮，就是 140 万 token，按 ¥4/M 计约 ¥5.60——这还只是 system 一项。Agent 场景里更狠：A02 那集任务回放里，每次工具观察（Observation）的全文都回灌上下文，几轮检索下来，历史比问题本身大几十倍。窗口消耗上去，首字延迟也跟着上去——输入越长，预填充越慢，这是长对话越聊越卡的根本原因。

## 上下文工程：有限预算里装什么

既然预算有限，「装什么」就成了工程决策，这便是「上下文工程」的要义。窗口里通常有四样东西争位置：系统提示（角色与边界）、历史消息、检索资料（R 模块课的主角）、输出余量。一种实用的做法是给预算定分配比例：例如 8192 的窗口，system 限 1500、检索资料限 2000、输出预留 2048，其余留给历史——比例随任务调，但必须显式定出来，而不是任由历史野蛮生长到报错才处理。取舍手法按性价比排序：其一，历史压缩——把久远的对话压成一段摘要，保住关键事实、释放大块预算；其二，检索精选——只放最相关的片段进窗口，而不是整篇文档；其三，给输出留足余量，别让回答被 length 截断；其四才是裁 system——这一项永远放最后，因为角色与边界是安全底线。

## 窗口是合同，不是记忆

最后把一个容易混淆的概念钉死：窗口给了模型「记得前文」的错觉，但它是合同不是记忆——每次请求都是一次性的，窗口里的内容随请求发出、随响应结束而消失，想留下来就得由应用自己存。这就是为什么「记忆」是一个独立的工程问题：滑窗、摘要、外部存储三种策略的取舍，A03 记忆课会专门展开。本课带走的实用结论只有三条：给每类内容定预算比例并写进配置；每次请求前先估 token 再发；盯住 finish_reason 与 usage 字段，别让截断和静默丢历史在无感知中发生。
