E 模块把 token 与成本算清楚了，T 模块让模型动起了手，P 模块回到更上游的问题：你怎么把需求说清楚，模型才不会做歪。同一个模型，prompt 的结构不同，产出质量可以差出一个世代——这不是玄学，是「需求表达」的工程学。上方的泳道时间轴用同一任务做了两次对照调用：一段话 prompt 对结构化 prompt，其余一切相同。

## 四件套：角色、任务、约束、格式

结构化提示的骨架是四件套。角色告诉模型「你是谁、用什么口吻说话」——它收窄了输出空间，客服助手与法务顾问的措辞边界完全不同。任务说清「做什么」，动词要具体：「抽取」「改写」「分类」都比「处理一下」可靠，后者把定义权交还给了模型。约束说清「边界在哪」：缺失字段填什么、日期用什么格式、不能碰哪些内容——约束是把业务规则前置到生成之前，让模型不必猜政策。输出格式说清「长什么样」：字段清单或 JSON Schema，这是四件套里杠杆最大的一件，下一节展开。四件套不必每次都全套上：闲聊式任务只配任务就够，但每一次调试输出质量，都先检查这四样里缺了哪样——缺的那一样，十有八九就是病根。

## 格式声明压住散文化

模型的默认惯性是对话：你给它一段话，它回一段话。要在对话惯性里拿到可入库的结构化数据，必须显式声明格式。演示里的 v1 就吃了这个亏——「把信息都提出来」得到了一段流畅的散文，4 个字段只可靠解析出 2 个。v2 加上「仅输出 JSON，字段：sender、deadline、priority、reply_by」，同一个模型立刻交出四字段齐整的 JSON。格式声明有两种写法：字段清单适合简单场景，列出名字与含义即可；JSON Schema 适合复杂场景，类型、必填、枚举、嵌套全都能表达，还能直接复用下游校验器的同一份定义——prompt 与校验共享一份契约，格式争议自然消失。格式声明的本质是把「输出空间」从无限收敛到有限：模型不再自由发挥写法，而是往你画好的格子里填内容。还有个常被忽略的细节：说清缺失怎么办——「取不到的字段填 null」这一句，能省掉下游一半的解析事故。

## 分隔符与结构降低读岔概率

prompt 一长，模型就可能「读岔」：把背景说明当任务、把示例当指令、把一段话的后半句与前半句的约束嫁接。分隔符是对策——用小节标题、三引号、XML 式标签或 Markdown 区块，把「背景」「任务」「资料」「格式要求」切成清晰区块，每块说一件事。比如把待处理资料整体包进 `<document>` 标签，指令放在标签外——模型处理长文档时，先按标签定位边界，再理解边界内的内容，读岔概率显著下降。读岔概率随结构化程度单调下降：模型对「哪部分是资料、哪部分是指令」的判别，主要靠结构标记而非语义猜测。长 prompt 里尤其要把资料与指令隔离——资料是被处理的输入，指令是处理的方式，两者混写等于让模型边做边猜规则。

## 一段话与结构化的差异在哪

把演示的对照读透：差异不在「礼貌」也不在「长度」，而在「谁定义输出」。一段话 prompt 把定义权留给模型——它按对话惯性写散文；结构化 prompt 把定义权收归需求方——字段、格式、边界都是显式的。质量差异因此系统性偏向结构化：不只是「这一次好一点」，而是「每一次都稳定」。对下游要接结构化数据的管线（校验、入库、统计），这个差异是能用与不能用的区别。同一套 prompt 换一个模型，结构化的版本迁移成本也低得多——字段清单在哪都是字段清单，散文风格却会随模型漂移。反过来，闲聊、头脑风暴、开放式写作并不需要四件套——对话惯性本身就是合适的输出形态，硬套结构反而别扭。

## 过约束的代价

结构化的反面是过约束。把输出钉得太死——字段类型卡到字符、篇幅卡到段落、措辞限制层层叠叠——模型会开始「硬凑格式」：为了凑齐字段编造内容、为了压进字数砍掉关键信息、为了符合模板牺牲事实准确性。准确性与格式服从发生冲突时，损失常常落在你看不见的那一侧：字段填齐了，但值是编的。所以约束要「够用就好」：每个字段都问一句「下游真的需要它吗」，每个限制都留一个「取不到就填 null」的出口，宁可让模型承认缺失，也别逼它虚构完整。修 prompt 的完整方法论——一次改一处、留存对照——在 P04 展开；这里只记一句：结构化是工具不是信仰，检验标准始终是下游校验与评估的通过率。
