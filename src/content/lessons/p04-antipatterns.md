前三课讲「该怎么做」，这一课讲「别怎么做」——prompt 工程的反模式比正面技巧更值得先学，因为它们太像本能：想客气一点、想把要求一口气说完、想用「不要」来禁止。它们还有一个共同点：出问题时不报错、不崩溃，只是让输出悄悄变差，所以格外需要专门的名单来对检。上方的泳道时间轴把三个高频反模式各摆了一场现场：超载指令漏做两项、否定式指令被照做、对照的正面改写达标收场。

## 客气话与威胁没有用

「请你务必」「这是非常重要的任务」「做不好会有严重后果」——这类句子是 prompt 里最常见的冗余。模型的对齐训练确实让它对礼貌请求给出得体的响应，但得体的响应态度不等于更强的能力：对齐训练塑造的是「响应的风格」，不是任务上的准确率，客气话与威胁对后者的贡献趋近于零，却稳定地消耗 token——每次请求都要重付的输入 token（E04/E05 的账单逻辑直接适用）。把「请你千万仔细」换成一句具体的约束（「缺失字段填 null」），效果立判。同理，「越狱式压测」——想方设法绕过模型的安全拒绝——在开发里满足好奇心可以，对生产质量没有任何贡献：生产要的是「正常请求下的稳定表现」，那是 G01 评估课的地盘。

## 超载指令：一句话塞十个任务

演示里的 v1 把五个要求塞进一句话，评估结果 3/5：要点列表缺失、正文 112 字远超 50 字上限——漏做时模型不会声明，它只是安静地少做。机理并不神秘：一句话里的并列要求越多，单个要求分到的「注意力份额」越少，排在句尾的要求最容易被挤掉；而且漏做的分布不稳定——这次漏的是要点，下次可能漏的是字数，同一个 prompt 时好时坏，正是这种不确定性最伤工程。修法是把指令清单化：一行一个要求，用编号固定边界，让每个任务都有独立的句法位置。清单化的本质与 P01 的分隔符一致——结构替代注意力去保证「每一件事都被读到」。需求天然复杂时，宁可拆成多轮调用，也别用一段话硬塞：每一轮只干一件事，串起来照样是完整流程。

## 否定式指令的陷阱

「不要用被动语态」的执行效果显著弱于「全部用主动语态写」。否定式指令要求模型完成一次额外的转换——先想到被禁止的表达，再抑制它——而「不要」这个前缀对注意力的抑制并不总是到位，演示里的 v1b 照样输出了被动语态。改成正面指令后，模型直接朝目标生成，连「先想后压」的环节都省了。正负转换是个可练习的技能：「不要输出长段落」→「每段不超过两句」；「不要编造」→「资料里没有的信息填 unknown」；「不要太啰嗦」→「正文控制在 50 字以内」。规则是把画面画给模型看，而不是描述画面的反面。示例（P02）与正面指令是同一哲学的两面：给样板，别给禁令。当然也有例外——安全红线类禁令（「绝不输出客户手机号」）该写还是要写，只是别指望一句「不要」独挑大梁，护栏（G03）才是最终防线。

## 过时与错配的示例

P02 说示例是行为规范，这一课补上它的阴影：规范会过时。产品改版后旧字段名留在示例里，模型会忠实地输出已废弃的格式；拿一个领域的示例去套另一个领域，模型会模仿出四不像。这两类问题在单次调试里几乎看不见——它们藏在「prompt 一直没改、世界一直在变」的时间里，往往要到下游或评估才炸出来。对策是把 prompt 当代码管理：示例纳入版本控制、与产品文档同步评审、变更留痕。凡是被放进 prompt 的东西——示例、字段清单、领域术语表——都要有人对它的时效负责。

## 修 prompt 的方法论

反模式清单的价值不在「记住几条」，而在给出修 prompt 的纪律：一次只改一处。同时改结构、换示例、加约束的「三连改」即使效果变好，你也说不清是哪个改动起效——下一次回归时无从回滚，这是比效果差更深的坑。每次修改留存前后对照：旧 prompt、新 prompt、两边的输出、评估结果，四样存档，改动与效果才能关联；等 G01 的评估集上线，这套对照记录会自动升级为回归测试的基线。这套纪律与代码审查同构：prompt 是会被反复修改的活文档，没有版本与对照的 prompt 调优，等于在没有版本控制的仓库里写代码。P 模块至此给齐了工具箱——结构（P01）、示例（P02）、草稿（P03）、纪律（本课）——接下来 R 模块换一个战场：给模型开卷考试。
